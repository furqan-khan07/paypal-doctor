# Rules

Every rule paypal-doctor ships is tied to something PayPal published: an API reference, an integration guide, the npm deprecation notice on its own packages, or its official sample code. If I couldn't point at a page, the rule didn't go in.

Each rule also has a probe: a scripted checkout that shows the bug happening on the unpatched app, and not happening after the patch. The one exception is `deprecated-sdk`, which is checked by re-scanning.

| Rule | Severity | What the detector looks for | How the probe proves it | Backed by |
|---|---|---|---|---|
| `client-supplied-amount` | critical | `purchase_units[].amount.value` (or `items[].unit_amount.value`) whose data flow reaches a price/total field of `req.body` / `await req.json()`. Follows local bindings, `reduce`/`map` callbacks, and call sites across files (two hops). | Sends a cart with the mug priced at $0.01 and checks what the app asked PayPal for. Pass = PayPal was asked for the catalog price ($18.00). | [Standard checkout integration](https://developer.paypal.com/studio/checkout/standard/integrate) ("pass data from the cart object to calculate the purchase units"); PayPal's [sample server](https://github.com/paypal-examples/docs-examples/blob/main/standard-integration/server/node/server.js) computes the amount server-side from the cart |
| `webhook-unverified` | critical | PayPal webhook routes (`app.post('/…webhook…')`, including handlers wired as `controller.method`, NestJS `@Post('webhook')`, Next.js `POST` in a webhook route) with no verify-webhook-signature / CRC32 / `crypto.verify` in the handler or the helpers it calls, followed four levels deep; or a verify call whose result is never compared to `SUCCESS`. Handlers about other providers (Stripe...), or that hand the headers to an SDK it can't see into, aren't flagged. | Posts a forged `PAYMENT.CAPTURE.COMPLETED` for a real order. Pass = order not marked paid. Also posts a correctly signed event and requires it to still be accepted (so "reject everything" doesn't pass). | [Webhooks: verify signatures](https://developer.paypal.com/api/rest/webhooks/rest/), [verify-webhook-signature](https://developer.paypal.com/docs/api/webhooks/v1/#verify-webhook-signature_post) |
| `capture-status-unchecked` | high | A capture call (fetch/axios/got, the app's own request helper, or the server SDK) where the function or a caller decides the payment is done (`.status = 'COMPLETED'`, a `"paid"`/`"captured"` status, `markPaid`...) and neither reads `captures[n].status`. A wrapper or server that only relays the capture isn't flagged. The webhook variant (`PAYMENT.CAPTURE.PENDING` treated as paid) is left to the LLM pass. | Three scenarios: a normal capture must mark the order paid; a capture whose response says `PENDING` (`PENDING_REVIEW`) must not; a card declined with PayPal's `CCREJECT-REFUSED` trigger must not. | [Orders v2 capture](https://developer.paypal.com/docs/api/orders/v2/#orders_capture), `capture_status` enum in the [Orders v2 spec](https://developer.paypal.com/api/orders/v2/schema.json) |
| `deprecated-v1-payments` | high | A string in a PayPal file naming one of the resources PayPal marks deprecated: `/v1/payments/{payment,sale,authorization,orders,capture,refund}`. `/v1/payments/payouts` is the current Payouts API, and other gateways have their own `/v1/payments` paths. | Captures an order, refunds it through the app, and checks the traffic. Pass = no `/v1/payments` calls and a successful `POST /v2/payments/captures/{id}/refund`. | [Payments v1 reference](https://developer.paypal.com/docs/api/payments/v1/): "The /v1/payments endpoint is deprecated" |
| `hardcoded-credentials` | high | A literal assigned to a secret name that's about PayPal: `PAYPAL_SECRET`, `paypal: { client_secret }`, or a client secret in a file that uses PayPal, including `process.env.X \|\| "literal"` fallbacks and literal `id:secret` pairs passed to `Buffer.from`/`btoa`. Other providers' keys, UI labels, placeholders and obviously fake values are ignored. Browser files are skipped (client ids are public). | Starts the app with credentials in the environment and checks the token request uses exactly those (by fingerprint). Then starts it with none and checks nothing baked-in gets sent. Always runs against the mock, so fake credentials never reach PayPal. | [Standard checkout: declare credentials as env vars](https://developer.paypal.com/studio/checkout/standard/integrate), [REST auth: "Keep this secret safe"](https://developer.paypal.com/api/rest/) |
| `amount-formatting` | high | `amount.value` built from float arithmetic, `reduce` sums, `Number()`/`parseFloat` without formatting (followed across call sites); `toFixed(2)` with JPY/HUF/TWD; decimal literals the currency doesn't allow; currency codes PayPal doesn't support. | Checks out 3 x $0.10 stickers. Pass = the app sent `"0.30"` and PayPal accepted it (the bug sends `"0.30000000000000004"` and gets `DECIMAL_PRECISION`). | [Currency codes](https://developer.paypal.com/reference/currency-codes/) (zero-decimal currencies), [Orders v2 errors: DECIMAL_PRECISION](https://developer.paypal.com/api/rest/reference/orders/v2/errors/), [`money.value` is a string](https://developer.paypal.com/docs/api/orders/v2/#definition-money) |
| `missing-request-id` | medium | POSTs to create/capture/authorize/refund/void without a `PayPal-Request-Id` header, or with a constant one, including calls through the app's own request helper and URLs held in a variable; server SDK calls without `paypalRequestId`; an order capture whose id changes on every call (`randomUUID()`, `Date.now()`), because a retry then isn't recognised as a retry. | **Capture:** PayPal processes the capture, the interceptor drops the response, the browser retries. Pass = the retry reuses the id and gets the original capture back (the bug gets `ORDER_ALREADY_CAPTURED` and the order is never marked paid, though the money was taken). **Create:** two checkouts get two distinct ids, and replaying one returns the same order. | [Idempotency](https://developer.paypal.com/api/rest/reference/idempotency/); `PayPal-Request-Id` is a declared parameter on create/capture/authorize/refund in the Orders v2 and Payments v2 specs |
| `hardcoded-environment` | medium | A sandbox or live API host literal, or `Environment.Sandbox` in the server SDK, that isn't a fallback behind config (`config.url \|\| "https://api-m.sandbox…"`), a named default, part of a sandbox/live switch, or only used to recognise a URL (`href.startsWith(host)`). | Starts the app with `PAYPAL_API_BASE` set to a canary host the interceptor routes to the upstream. Pass = every PayPal call went to the canary. | [Go live checklist: "Update your PayPal endpoint"](https://developer.paypal.com/studio/checkout/standard/integrate), [live host](https://developer.paypal.com/api/rest/production/) |
| `deprecated-sdk` | medium | `paypal-rest-sdk` or `@paypal/checkout-server-sdk` in package.json, `import` or `require`. | Static re-scan only. | npm deprecation notices on [paypal-rest-sdk](https://www.npmjs.com/package/paypal-rest-sdk) and [@paypal/checkout-server-sdk](https://www.npmjs.com/package/@paypal/checkout-server-sdk), both pointing to `@paypal/paypal-server-sdk` |

## A note on `client-supplied-amount`

PayPal's docs describe the server building the purchase units from the cart, and the official sample does exactly that. They don't say in so many words "never trust a price from the browser". I kept the rule because it's the most expensive bug on the list. The probe doesn't rest on the docs' wording anyway: it shows the app asking PayPal for $0.01.

## Considered, not shipped

I wasn't able to tie these to a PayPal page tonight, or to build a probe that proves them, so they stay out until I can:

- Webhook handlers that don't dedupe on `event.id` (PayPal retries deliveries).
- Refund amount taken from the client.
- The JS SDK `currency=` query param not matching the order's `currency_code`.
- Legacy IPN listeners that skip the `cmd=_notify-validate` postback.
- `intent: AUTHORIZE` orders that are never captured or voided.
